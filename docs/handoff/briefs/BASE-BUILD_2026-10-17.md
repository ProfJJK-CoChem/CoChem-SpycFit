### Options
Letters are this brief's; `docs/handoff/PI_DECISIONS.md` has no BASE-BUILD row.
- **A. BASE owns it:** `scripts/provision_pickett.py`, `scripts/pickett-distribution.json`, the receipt above, `cochem-cli pickett build|verify|status`, workflow `pickett_build.yml` (`ubuntu-24.04`, as `cochem_base_ci.yml` l.36); edits to `hosted_dashboard.py`, `cli.py` (l.1019-1073), `cochem_system_config.py`, `spcat_runner.py`, `devcontainer.json`, `module-distribution.json`, `pytest.ini` and the ring. BASE owns the pin; TORQ's inventory follows.
  - Pros: one manifest, one receipt, one home for XIAM/ERHAM; matches the PI's wording.
  - Cons: largest BASE change, ring refresh and `pytest.ini` in one PR; TORQ must accept a second schema (a PI request).
  - Risks: a JPL byte change needs coordinated updates in three repositories.
- **B. TORQ's `provision_pickett_validation.py` is the provisioner; BASE calls it from the installed TORQ module.** TORQ owns the pin.
  - Pros: hardened and CI-proven; no new script.
  - Cons: two-program, Linux-ELF receipt with no acceptance run; DPFIT/DPCAT, XIAM and ERHAM become TORQ changes; BASE's TORQ pin lacks it.
  - Risks: SpycFit's provenance depends on TORQ releases.
- **C. Per-module provisioners:** TORQ keeps its script, SpycFit ships its own (SF-RUN-009, l.472-475), BASE only wires `cochem-cli` to whichever module is installed. Two pin owners.
  - Pros: smallest BASE change; standalone SpycFit on HPC has its provisioner.
  - Cons: two manifests and builds; D-SPYC-16 E would need a later convergence step; BASE's fallback survives.
  - Risks: adapter and hash drift, the problem D-SPYC-16 named.
- **Hook mode.** H1 automatic in `setup_devcontainer.sh`: Pros, no command for students; Cons, conflicts with TORQ's rule (l.46-48) while SF-RUN-008 rights are unrecorded; Risks, every image downloads from JPL. H2 opt-in `cochem-cli pickett build` (Caltech notice shown): Pros, fits TORQ's rule and BASE's optional-engine rule (l.26-28); Cons, comparisons stay UNAVAILABLE until run; Risks, unbuilt images in class. H3 off (CI only): Pros, nothing provisioned before rights are recorded; Cons, no student path.
- **`spcat_runner` fallback.** F1 removed in the same BASE PR; F2 a separate PR; F3 left, recorded as never-SPCAT per D-SPYC-16 D.
- **`hcotst.par` chain for V-PICK-05.** Y satisfies it while `hco.var` is unavailable, recorded as a listed difference; N wait for `hco.var`.

### Agent recommendation
A, staged, with H2 and F1: the first BASE PR builds the four programs with `make -j1 spfit spcat dpfit dpcat`, writes the receipt, keeps the hook opt-in and removes the in-process fallback, because TORQ's accepted text blocks automatic student provisioning until rights are recorded. gfortran and XIAM follow in a second PR once XIAMALL.FOR's and ERHAM's terms are read. Main risk: the hash ring and `pytest.ini` make every BASE edit all-or-nothing, and TORQ's agreement to a second schema is unrecorded. Reduce it by listing each touched file and the ring refresh in the PR description, uploading only receipt and log hashes, keeping programs off PATH, and asking the TORQ maintainer. DPFIT/DPCAT stay `built` until the NO differences are explained.
