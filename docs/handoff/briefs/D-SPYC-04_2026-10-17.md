### Options
**A. Wrap named engines; no native model; any later one by amendment.**
- Pros: least code; follows MM's protocol.
- Cons: native P4 comparisons stay NOT_RUN (SF-CMP-020); windows need external runs.
- Risks: Linux only until BASE adds gfortran; unmaintained Fortran.

**B. Full native model, IAM or RAM (this sets the reference); implies D-SPYC-18 C (PD l.351).**
- Pros: offline, cross-platform; fast interactive A/E assignment.
- Cons: largest effort; SF-HAM-001 (l.673) needs IAMCALC as reference or an amendment.
- Risks: a model accepted on few cases is used beyond its tested barriers.

**C. Defer the choice until semirigid acceptance.**
- Pros: no P4 engine work before P1.
- Cons: P4 names no engines under SF-CMP-019.
- Risks: late P4 requirements.

**D. Native terms that SPCAT reproduces (effective PAM; IAMCALC later), checked under SF-HAM-001; within D-SPYC-18 B.**
- Pros: applies the PI's SPCAT/SPFIT principle as written; parameter-level checks.
- Cons: suits sizable barriers and low J; V3 only via Herschbach's tables; IAMCALC `.par` files are "completely unreadable".
- Risks: effective constants mistaken for a barrier fit.

### Agent recommendation
A, with XIAM first and ERHAM second; BELGI, RAM36 and westerfit listed as later, so SF-CMP-019 names only provisioned engines. XIAM is MM's engine and the benchmark's, has written use terms and built unchanged locally; ERHAM covers motions that are not threefold. Wrapping is the agent's way to meet SF-PHYS-005 and SF-CMP-019; neither requires it. D can follow via the D-SPYC-18 terms brief. Main risk: variant and provisioning; name the variant, build in Actions, and accept against posted examples on scratch copies recorded by URL and SHA-256. Low barriers lack a RAM reference until BELGI or RAM36 is provisioned.
