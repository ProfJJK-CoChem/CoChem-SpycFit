### Question
Which, if any, of the three operation names that CoChem-BASE declares for SpycFit (`pickett_export`, `pgopher_export`, `spectroscopy_snapshot`) will SPYFY provide, under that name or a new one, and what does each answer ask of BASE?

### Why it matters now
SpycFit lines are at `80ecfa2`; BASE lines at the local clone `7d5b8ac`; TORQ lines at `05bf2b3`.
- Proposed SF-IF-004 asks for this answer before G1 (`docs/srs/CoChem-SpycFit_SRS_v2.md` l.567-570); SF-IF-002 (l.561-563) and SF-IF-005a (l.539-541) depend on it.
- Architecture §1 says SRS v2 §4.4 "must accept, rename or retire" them (`docs/architecture/CoChem-SpycFit_Architecture.md` l.34-37); the `export` row (l.63) separately waits on "BASE adding the handoff kind" (D-SPYC-03). Plan WP-IF (`docs/plan/CoChem-SpycFit_Plan.md` l.51-53) and G1 (l.15) wait on it.
- Terms: *accept* = SPYFY provides the name; *rename* = a name it chooses; *retire* = no such operation.

### Context
- **What the files are.** Three 17-line shells with `module_id='spycfit'` and one operation each (`CoChem-BASE/src/cochem_base/interfaces/cochem_pyckett_bridge.py`, `cochem_pgopher_bridge.py`, `cochem_vibspyc_snap.py` l.8-9), each a "compatibility entrypoint" that "does not execute the former advertised solver or service API" (l.3-4).
- **Direction.** BASE's docstrings call the first two "downstream spectroscopy export" contracts (l.1): BASE exports *to* SpycFit. Reversed, the names promise outputs the one-artifact, no-execution manifest cannot carry (`artifact_handoff.py` l.37, l.39).
- **What the manifest carries.** Four kinds: `geometry_xyz`, `cartesian_hessian`, `calculation_result`, `periodic_structure` (l.20). Only `.json` files meeting the `calculation_result` checks are accepted (l.93-117); every other suffix, so `.par`, `.var`, `.lin`, `.int`, `.cat`, is rejected (l.118). None of SPYFY's inputs or outputs has a kind. The `operation` field accepts any name matching `^[A-Za-z][A-Za-z0-9_.-]*$` (l.34), so SRS v2 names need no BASE schema change.
- **Who uses them.** No production code: `_ADAPTERS` covers TOPOS and TORQ only (`module_execution.py` l.23-28); the distribution manifest lists SpycFit with `adapter: null`, `operations: []` (`scripts/module-distribution.json` l.149-156). One collected test exercises them (`tests/base/test_legacy_interface_boundaries.py` l.7-11); three uncollected `test_suite/` files import names the shells no longer define (`test_suite/test_cochem_pyckett_bridge.py` l.55); one BASE doc line describes the shells. No TORQ file or maintainer statement names them.
- **Snapshot successor.** The snapshot exporter exists only in SpycFit's legacy tree (`src/cochem_spycfit/interfaces/cochem_vibspyc_snap.py` l.873), with AASTeX longtables, BibTeX from CrossRef and sealed archives (l.1-13). The review lists it under DISCARD (`docs/wiki/review/CoChem-SpycFit_SRS_Review.md` l.536, l.865), a recommendation only; porting or discarding it is D-SPYC-15, OPEN (`docs/handoff/PI_DECISIONS.md` l.40). SF-PUB-001a/b (l.1378-1386) do not require those formats. Renaming `spectroscopy_snapshot` presumes a successor.
- **Common to every option.** Before SPYFY receives work through BASE, BASE needs input kinds for spectra, peak lists and Pickett files (D-SPYC-19: "there should be a way to input the predicted ... orca files or SP um Cat SP fit files", `docs/decisions/D-SPYC-19.md` l.15-19); a multi-file handoff (a fit needs `.par` plus `.lin`; one artifact per manifest, `artifact_handoff.py` l.37); an adapter; and distribution-manifest entries. The provider contract is written for TORQ (handler in `cochem_torq.*`, `.docs/Module_Provider_Contract.md` l.50; an electronic-structure execution boundary, l.63). Each is a BASE change only the PI can request (`AGENTS.md` l.42-43), as is deleting BASE's files. The registry description "Spectroscopy fitting and export" (`interfaces/module_registry.py` l.46) is outside every option; the D-SPYC-22 rename request (`docs/decisions/D-SPYC-22.md` l.34-38) edits that line, where the PI can decide whether "export" stays.
- **Conflict.** SF-IF-002 says SpycFit receives work "only through `cochem.module-handoff/1` manifests" (l.561-563), yet that manifest rejects the files SF-IF-005a requires (l.118). Two resolutions: (i) under hosting H2 (`docs/decisions/D-SPYC-05.md` l.21-22) the user supplies files inside the SPYFY notebook and SF-IF-002's "only" clause changes; (ii) BASE ingests them ("CoChem-BASE though is a hard requirement cuz that has the ingestion and the unified GUI", D-SPYC-19 l.18-19) and adds Pickett kinds. SRS v2 names neither.
- **SRS coverage.** Pickett files: SF-IO-004a (l.432-435). No requirement writes PGOPHER files, but PGOPHER is a reference engine for P2, P3, P6, P7 (l.173-178) and is named in the no-fallback rule (`AGENTS.md` l.50-53). D-SPYC-01 records "Option C (a PGOPHER front end) was not chosen. The PI gave no reasons." (`docs/decisions/D-SPYC-01.md` l.41). PGOPHER (Western 2017, doi:10.1016/j.jqsrt.2016.04.010) itself imports `.cat`, `.lin` and "many parameter (.par) files" (https://pgopher.chm.bris.ac.uk/Help/linformat.htm, read 2026-10-17); its home page announces no further updates (23 Mar 2022, https://pgopher.chm.bris.ac.uk/).

### Options
**A. Accept all three names.**
- Pros: BASE's compatibility CLIs and test keep working.
- Cons: `pgopher_export` has no SRS requirement; "export" names on BASE-to-SPYFY handoffs mislead.
- Risks: names chosen before the SRS fix SPYFY's operation set.
- BASE changes: common set plus three export kinds.

**B. Rename two, retire one.** `pickett_export` becomes SPYFY's Pickett *input* operation (route ii); `spectroscopy_snapshot` becomes the publication-package operation (SF-PUB-001); `pgopher_export` is not provided.
- Pros: matches D-SPYC-19's ingestion statement and D-SPYC-01 l.41; keeps two BASE entry points.
- Cons: presumes D-SPYC-15 settles the snapshot successor.
- Risks: a Pickett operation fed a geometry reads as SPYFY predicting from computed constants, which D12 (`CoChem-TORQ/docs/wiki/review/Decisions_and_Risks.md` l.135: "the full rotational-spectroscopy route is TORQ scope") and TORQ SRS l.25 give TORQ; since D-SPYC-16 D (SRS l.212-217) and SF-IF-005a already allow it, the risk is labelling, not ownership.
- BASE changes: common set plus a multi-file Pickett kind and a package kind; one shell removed, two edited; one test parameter, three uncollected tests, one doc line.

**C. Provide none of the three names.** SF-IF-004 records each as not provided; SPYFY publishes its operations through `cochem.modules` (SF-IF-002).
- Pros: uses BASE's existing mechanism; no export kinds; names follow SRS v2 once it carries the PI's `srs-v2.0` tag.
- Cons: the `export` row still needs D-SPYC-03's request kind; the SRS needs the operation list.
- Risks: two sets of names coexist while BASE keeps the shells.
- BASE changes: common set only; cleanup, if the PI requests it: three source files, three test parameters, three uncollected tests, one doc line.

**D. Drop SF-IF-004.** SF-IF-002 lists SPYFY's operations; the BASE names go to the PI as a cross-repository note.
- Pros: no requirement about another repository's code.
- Cons: nothing in SPYFY prevents later reuse of the old names.
- Risks: the disposition is undocumented. BASE changes: common set.

### Agent recommendation
Option C. None of the three can carry SPYFY data, no production code calls them, and SPYFY can declare its own operations under any valid name; the Pickett set and publication package stay required as outputs (SF-IO-004a, SF-PUB-001). Main risk: duplicate names while the shells remain in BASE. To reduce it, SF-IF-004 lists each name as not provided, a SpycFit test checks that the published operations exclude them, and the cleanup count goes to the PI as a separate BASE item. The SF-IF-002 versus SF-IF-005a conflict needs the PI's route (i or ii) in the same answer; the snapshot features wait on D-SPYC-15.

### How to answer
"SF-IF-004: C; route ii" (or "route i"). Or per boundary, for example "SF-IF-004: pickett_export rename (input), pgopher_export retire, spectroscopy_snapshot rename".
