### Question
How should SpycFit send theory-feedback requests (recompute requests to TORQ; inverse PES or force-field fits to an unnamed provider): by BASE handoff, by user-carried file, or into a task queue?

### Why it matters now
Lines are at branch head `fadb028`; SRS is `docs/srs/CoChem-SpycFit_SRS_v2.md`.
- SF-RUN-005a is "blocked on D-SPYC-03" (SRS l.1316-1320). SF-RUN-005b (l.1321-1323), UC-6 (l.374), RefinementRequest (l.1348), P14 (l.170), SF-ML-003a (l.960-962) and the §1.3 TORQ row (l.182) depend on it.
- Every option must meet SF-SCOPE-005 (§4.3, l.489-491): exchange "only through the versioned provider interface".
- A BASE route needs a new §4.4 requirement. The architecture `export` row already assumes A (`docs/architecture/CoChem-SpycFit_Architecture.md` l.60); plan WP-OUT carries the work (`docs/plan/CoChem-SpycFit_Plan.md` l.49). The GEOM payload (SF-IF-008, l.600-604) needs a route too.

### Context
- Settled: refinement is required and "may be implemented in another CoChem module" (`docs/HANDOFF.md` l.25). Baseline SF-RUN-005 requires refinement requests (`docs/wiki/CoChem-SpycFit_Comprehensive_SRS.md` l.164).
- TORQ produces vibrational and Raman predictions (D-SPYC-06, `docs/decisions/D-SPYC-06.md` l.20-21; awaits PR approval), so it likely receives all recompute requests. No module owns inverse fits: TORQ's "refinement" is geometry refinement and ab initio PES sampling (TORQ SRS, `CoChem-TORQ/docs/wiki/CoChem-TORQ_Implementation_SRS.md` l.240, l.403). TORQ's "refinement request" already names scan candidates (`src/cochem_torq/cli.py` l.165-167); SpycFit needs another name.
- BASE is required (D-SPYC-19, `docs/decisions/D-SPYC-19.md` l.15-19); SpycFit receives work only through handoff manifests (SF-IF-002, l.518-519).
- A BASE handoff carries one artifact of four kinds (`CoChem-BASE/src/cochem_base/interfaces/artifact_handoff.py` l.20, l.37; unchanged at BASE `main` `b117ca4`). Only the artifact is hashed and inspected; `options` get a JSON check (l.171-181). A `.json` artifact must report convergence and an energy (l.93-101).
- TORQ: one task authority (TORQ-ARC-002, l.102; D08, `CoChem-TORQ/docs/wiki/review/Decisions_and_Risks.md` l.87-91); model changes need an approved plan (TORQ-PLAN-003, l.218). Its `cochem.torq.request/1` requires a `recipe` and carries scalar experimental anchors (uncertainty, `data_usage`) (`src/cochem_torq/domain.py` l.139-149; `scientific_contracts.py` l.125-137). Envelopes (P7, P8) do not fit a scalar anchor.
- Inverse fits use measured data: morphing fits by least squares (Meuwly & Hutson 1999, doi:10.1063/1.478744); scaled force fields use experimental frequencies (Pulay et al. 1983, doi:10.1021/ja00362a005). Agent inference: weighted fits need assigned observables with uncertainties, as review ARCH-09 asks (`docs/wiki/review/CoChem-SpycFit_SRS_Review.md` l.262).
- **Does the 2026-10-11 recommendation fit?** Its mechanism does: a versioned file through BASE, human-approved (`docs/handoff/PI_DECISIONS.md` l.116). Its scope does not: rotational recompute requests to TORQ only.
- A, A2 and D all keep TORQ's task authority and plan approval (TORQ-UI-001, l.401).

### Options
**A. Request file as a new BASE handoff kind; a human approves the receiver's plan.**
- Pros: BASE hashes and checks the request; lineage in BASE (D08).
- Cons: BASE adds a kind and validator (precedent: `periodic_structure`, `20b7732`), relaxes its `geometry_xyz`-only executor check (`module_execution.py` l.208-209), and per receiver an adapter, operation and pin. TORQ needs an SRS change and a consumer.
- Risks: no end-to-end run until both ship; hosted runs would need a private repository, as TOPOS does (`module_request.py` l.93-94).

**A2. Request in handoff `options` beside a `geometry_xyz` artifact; BASE adds a reviewed operation.**
- Pros: no BASE schema change; TOPOS precedent (`scripts/module_request.py` l.52-61); TORQ's reader accepts the artifact (`cochem_torq/ecosystem.py` l.620-624).
- Cons: BASE neither hashes nor schema-checks `options`; TORQ still needs a consumer.
- Risks: integrity rests on the receiver; large observable sets bloat `handoff.json`.

**C. Direct queue submission.**
- Pros: least manual work.
- Cons: C1, writing another module's task database, breaks TORQ-ARC-002 (review ARCH-10, l.263). C2, a versioned BASE task-service API, fits D08 in principle but does not exist (BASE's `sqlite_queue.py` is unversioned and internal).
- Risks: TORQ-PLAN-003 approval is skipped unless built in.

**D. Request file only; the user carries it (B plus a versioned file).**
- Pros: SF-RUN-005a ships without a new BASE kind or receiver.
- Cons: no BASE lineage record; bypasses BASE ingestion and GUI, your reason for requiring BASE.
- Risks: hand-carried results enter by direct input, labelled user-supplied (SF-IF-005c, l.504-506), losing the link to the request.

B (no feedback path) is omitted per Context bullet 1 and the agent's record (`docs/decisions/D-SPYC-03.md` l.28); you can still answer B.

Return: TORQ bundles come through SF-IF-001, blocked on TORQ's exporter (l.492-495); outputs should echo the request id and SHA-256 so SF-RUN-005b links it.

Schema owner (any option): (i) SpycFit drafts it, agreed with each receiver by consumer tests in both repositories (review ARCH-10, l.263; TORQ-EXP-004, l.332); (ii) TORQ-bound requests use `cochem.torq.request/1`; (iii) BASE hosts it.

### Agent recommendation

Amend it to carry assigned observables, uncertainties and `data_usage`. Then add a §4.4 BASE requirement, blocked on BASE and a receiver; inverse-fit routing waits for a provider.
